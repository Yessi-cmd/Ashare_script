# 阶段 5：性能优化

状态：`COMPLETE`
完成日期：2026-07-18

## 目标

在真实数据量和服务器资源上测量瓶颈，再通过批量处理、缓存和索引满足明确的性能预算。

## 优化方向

- 全市场实时行情每轮只获取一次。
- 日线按交易日增量同步，盘中不重复下载完整历史。
- 指标批量或向量化计算。
- 有界并发获取缺失数据，限制外部 API 压力。
- Web 只读取预计算快照，图表按需加载。
- SQLite WAL、busy timeout、复合索引和短事务。
- 缓存命中率、外部 API 延迟、策略耗时和页面延迟指标。

## 初始性能预算

- 个人关注池单轮计算：目标小于 2 秒，不含外部 API 超时。
- 本地缓存命中的股票详情页：目标 P95 小于 300ms。
- 本地缓存命中的总览页：目标 P95 小于 200ms。
- 全市场候选扫描不得因单个股票失败而阻塞整轮。
- 监控常驻内存和数据库增长必须可观测。

## 验收方法

- 固定数据集上的可重复 benchmark。
- 优化前后保留结果对比。
- 性能提升不得改变策略结果或降低数据正确性。

## 首轮基线与实施计划

- 19 股 V3 + 沪深 300、5 个阈值、单次训练/验证的 wall time 基线为 47.90 秒。
- 本地认证总览 HTTP 响应约 17ms，已满足 200ms 预算；先不引入 Redis 或 PostgreSQL。
- 第一优化项：每只股票、每个交易日只计算一次确定性评分，阈值扫描复用日期到评分的 trace；收益模拟仍分别执行，确保信号穿越语义不变。
- 第二优化项：数据库 schema 初始化在单进程内只执行一次，避免批量载入 19 只股票时反复 `create_all` 和索引检查。
- 为评分 trace 增加等价性测试，优化前后回测交易和汇总必须完全一致。
- 优化后使用同一命令、同一缓存和同一机器复测，记录 wall time 与加速比。

## 实施结果

- 回测引擎新增按股票/交易日的评分 trace；阈值扫描直接复用分数，不再重复构造历史窗口。
- V3 市场环境贡献按沪深 300 日期预计算，所有股票复用；回测专用 scorer 对已标准化窗口跳过重复字段清洗。
- 数据库 `create_all` 与唯一索引检查改为进程内线程安全的一次性初始化，批量读取不再重复执行 schema 检查和日志。
- 新增 `performance_benchmark.py`，可重复测量本地总览查询和指定股票池的纯 V2 评分 P50/P95。

## 验证与测量

- 相同 19 股、相同 614 根日线、相同沪深 300、5 个阈值和相同训练/验证区间：`47.90s → 22.18s`，wall time 降低 53.7%，约 2.16 倍加速。
- 优化前后所有候选阈值交易数、胜率、平均收益、回撤、盈亏比和最终选中阈值完全一致。
- 19 只股票的纯 V2 本地评分：P50 29.67ms，P95 33.36ms，远低于 2 秒预算（不含外部 API）。
- 本地认证总览真实 HTTP 响应约 17ms，低于 200ms 预算；浏览器页面无横向溢出和控制台错误。
- Ruff、编译检查和累计 46 项离线测试通过。

## 后续性能边界

- 研究任务 22 秒仍主要消耗在逐日 Pandas 因子计算；只有在股票篮子继续扩大后才值得把 V3 全量向量化或使用 NumPy/Numba。
- 当前个人规模不需要 Redis/PostgreSQL；引入额外服务会增加部署与恢复成本，且没有测量证据支持。
- 外部行情延迟仍由公开数据源决定，已通过超时、重试、备用源和本地缓存隔离，不能靠本地微优化消除。
